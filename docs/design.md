# llm-api-test CLI design (refactor)

A CLI to test LLM API compatibility across API formats (chat, responses, messages)
and to benchmark latency/throughput. Greenfield design — no constraints from the
current implementation.

## Exit codes

- `0` — all tests passed
- `1` — at least one test failed
- `2` — config or argument error

## Common flags (all subcommands)

```
      --base-url string      base URL, overrides config `base_url`
      --api-key string       API key, overrides config `api_key`
  -m, --models stringArray   models to test, overrides config `models`
  -c, --config string        path to config file (default "config.yaml")
      --no-stream            disable streaming (default: requests are streamed)
      --http-debug           dump HTTP request/response to stderr (sensitive headers redacted)
  -o, --out string           write the JSON report to this file; text report still goes to stdout
  -v, --verbose              print raw response body on each case
  -h, --help                 help
```

Notes:
- Default is to run **all** tests, streamed. Stream compatibility is therefore
  implicit: every request streams, so an endpoint that does not support SSE
  fails the tests.
- `--no-stream` sends non-streamed requests. In benchmark mode, stream-only
  indicators (TTFB/TTFT/TPOT) are omitted from the report.

## Subcommands

- `compatibility [tests...]` — run compatibility tests (selection rules below)
- `latency` — run latency benchmarks (short pong prompt)
- `throughput` — run throughput benchmarks (long prompt)
- `cache` — run cache hit-rate tests (session-shaped; chat/messages)
- `list` — list available compatibility tests, grouped by API format
- `completion` — shell completion script (auto-generated by cobra)
- `help` — auto-generated by cobra

## Test organization

Each compatibility test has a stable ID: `<format>:<name>`, e.g. `chat:seed`,
`responses:text.format`, `messages:cache_control`.

- chat:      `basic`, `system-message`, `response_format`, `seed`, `tool-call`
- responses: `basic`, `instructions`, `reasoning`, `text.format`, `text.verbosity`, `prompt_cache_key`, `tool-call`
- messages:  `basic`, `system`, `thinking`, `cache_control`, `tool-use`

`compatibility [tests...]` selection rules:

- no arguments — run all tests for the selected formats (`--api-format`)
- `chat:seed` — run that exact test
- `seed` — bare name: run all tests named `seed` in the selected formats; error if none match
- `chat` — format namespace: all chat tests

This scales as fields are added: a new field is one entry in the format's
ordered test list plus its ID in `list` output — no new CLI surface.

## compatibility

Flags:

```
      --api-format string   API format to test: all, chat, responses, messages (default "all")
```

By default all formats are tested; `--api-format chat` limits to one format.

Per format, tests run in order: basic → body fields → tool call. If the basic
test fails, the format is marked unsupported and the remaining tests are
skipped (reported as `support: false`, detail `skipped: basic failed`).

### chat (POST /v1/chat/completions)

1. `chat:basic` — returns an assistant message
2. Body fields (only a few for now):
   - `system-message` — accepts and follows a system message
   - `response_format` — accepts `response_format` (json_object) and returns JSON
   - `seed` (De Facto Standard) — accepts `seed`
3. `chat:tool-call` — supports custom function tools (tool_calls output)

### responses (POST /responses)

1. `responses:basic` — returns output text for a simple prompt
2. Body fields:
   - `instructions` — accepts `instructions` and follows them
   - `reasoning` — accepts `reasoning.effort` and `reasoning.summary`
   - `text.format` — accepts `text.format` (json_schema) and returns schema-conformant JSON
   - `text.verbosity` — accepts `text.verbosity`
   - `prompt_cache_key` — accepts `prompt_cache_key`
3. `responses:tool-call` — supports custom function tools (function_call output)

### messages (POST /v1/messages)

1. `messages:basic` — returns a text content block
2. Body fields:
   - `system` — accepts and follows a system prompt
   - `thinking` — accepts `thinking` (extended thinking)
   - `cache_control` — accepts `cache_control` on system blocks
3. `messages:tool-use` — supports custom function tools (tool_use content block)

## latency / throughput

Two commands that share the benchmark runner, flags, and report format; they
differ only in the prompt and which indicators are reported.

Flags (both commands; defaults differ — latency 5x10, throughput 3x3):

```
      --api-format string   API format to test: all, chat, responses, messages (default "all")
      --concurrency int     concurrent requests per iteration (default 5 / 3)
      --iterations int      iterations per benchmark case (default 10 / 3)
```

Throughput defaults to 3x3 because each request is expensive (long prompt,
~1 min each); latency requests are cheap so it defaults to 5x10.

`latency` uses the short pong prompt and reports TTFB/TTFT/Total;
`throughput` uses the long article prompt and additionally reports
TPOT/TPS/tokens. One benchmark case per format (`chat`, `responses`,
`messages`); each runs `iterations × concurrency` requests.

TODO: reasoning-load benchmark — a prompt preset that deliberately triggers
long reasoning (complex multi-part prompt) to measure end-to-end throughput
under reasoning-heavy workloads. The current throughput prompt is
intentionally simple (fixed-length article) so TPS/TPOT mostly measure
steady-state generation; a reasoning-load case sits at the other end of the
spectrum: TTFT-dominated, higher variance, much higher token cost.

### Indicators

All latency indicators are reported as p50/p95/p99/min/max.

| Indicator | Meaning |
|---|---|
| TTFB | time to first byte of the HTTP response |
| TTFT | time to first parsed token |
| Total | end-to-end request latency |
| TPOT | time per output token (throughput mode) |
| TPS | output tokens per second (throughput mode) |
| RPS | requests per second (`total_requests / elapsed`) |
| Tokens | prompt / completion token counts (throughput mode) |
| Output | avg content bytes and chunk count (throughput mode) |
| Failed | count of non-2xx / timeout / parse failures |

`--no-stream`: TTFB, TTFT, TPOT are omitted (they require streaming); Total,
RPS, Failed are still reported; throughput falls back to tokens/s derived from
the `usage` fields.

### Text report (example)

```

  benchmark-chat  (10 iters x 5 concurrency = 50 requests)
    TTFB:  p50=180ms p95=410ms p99=590ms min=120ms max=620ms
    TTFT:  p50=210ms p95=450ms p99=620ms min=150ms max=680ms
    Total: p50=380ms p95=620ms p99=890ms min=250ms max=950ms
```

`-o report.json` writes the machine-readable report; the text report still goes
to stdout. The Go structs below are the source of truth — the JSON examples are
derived from them. All durations are integer milliseconds; rates are floats.

## Implementation

### Directory layout

Format-first: one top-level package per API format, named after the
`--api-format` value. The compatibility/benchmark split lives at the runner
level, not in directories — each format's cases and its benchmark share the
client and request-building code in one package.

```
cmd/llm-api-test/              main.go — os.Exit(cmd.Execute())
internal/
├── chat/                      OpenAI Chat Completions (POST /v1/chat/completions)
│   ├── client.go              request/response types, Send (stream or plain)
│   ├── stream.go              SSE parsing + TTFB/TTFT/TPOT instrumentation
│   ├── cases.go               Format() descriptor
│   ├── basic.go  system_message.go  response_format.go  seed.go  tool_call.go
│   └── benchmark.go
├── responses/                 OpenAI Responses (POST /responses) — same shape
├── messages/                  Anthropic Messages (POST /v1/messages) — same shape
├── openai/                    shared OpenAI HTTP plumbing (auth, --http-debug,
│                              Do/PostJSON); used by chat and responses
├── registry/                  shared types only (no format imports):
│                              Format, CompatCase, BenchmarkCase, CompatResult,
│                              Metrics, Params
├── runner/                    format-agnostic: RunCompat (basic gating),
│                              RunBenchmark (waves), percentile aggregation,
│                              text + JSON reporters
├── cases/                     shared helpers: Pass/Fail/FailRaw, MustJSON,
│                              PongPrompt/LongPrompt
├── config/  sse/  httpx/      plumbing (kept)
└── cmd/                       cobra root + compatibility/latency/throughput/list;
                               composition root (format list lives here)
```

### Key types (internal/registry)

```go
type CompatResult struct {
	Pass   bool
	Detail string // failure reason; "skipped: basic failed" when gated
	Raw    string // response body, shown with --verbose
}

type CompatCase interface {
	ID() string   // e.g. "chat:seed"
	Name() string // e.g. "seed"
	Desc() string
	Run(ctx context.Context, model string) *CompatResult
}

// Metrics captures timing and token data from one benchmark request.
// TTFB, TTFT, and TPOTs are only measured for streamed requests.
type Metrics struct {
	TTFB             time.Duration
	TTFT             time.Duration
	Total            time.Duration
	TPOTs            []time.Duration // time between consecutive content chunks
	CompletionTokens int
	PromptTokens     int
	ContentBytes     int
	Chunks           int
	Err              error // non-nil when the request failed
}

type BenchmarkCase interface {
	ID() string
	Desc() string
	Run(ctx context.Context, model, prompt string) *Metrics
}

// Params carries run-wide settings into format construction.
type Params struct {
	Config *config.Config
	Stream bool
	Debug  io.Writer // --http-debug dump target
}

type Format struct {
	Name      string
	Desc      string
	Cases     func(Params) []CompatCase // ordered: basic first
	Benchmark func(Params) BenchmarkCase
}
```

### Flow

1. `cmd` resolves `--api-format` against the format list (the composition
   root in `internal/cmd`; the registry is types-only to avoid an import
   cycle with the format packages).
2. The format package builds its cases from `Params` — each case closes over
   its client. Cases construct requests at `Run` time from the model.
3. Compatibility: `runner.RunCompat` runs the ordered case list. The first
   case is the format's basic test; when it fails, the remaining cases are
   skipped.
4. Benchmark: `runner.RunBenchmark` runs `iterations` waves of `concurrency`
   parallel requests and aggregates percentiles (p50/p95/p99/min/max).
5. Reports: text goes to stdout; `-o` writes the JSON reports (schema above),
   one object per (model, format) run.

### Implementation decisions

- **`Metrics` lives in `registry`, not `runner`** — `BenchmarkCase.Run`
  returns it, so the format packages and the runner share it.
- **Format list is assembled in `internal/cmd`** (composition root) — the
  registry package stays free of format imports, so there is no import cycle.
- **Basic-gating is a convention**: the first entry of `Format.Cases` is the
  basic test.
- **`messages` has its own client** — it authenticates with `x-api-key` +
  `anthropic-version` instead of Bearer; `chat` and `responses` share
  `internal/openai`.
- **TPOT is measured as the time between consecutive SSE content chunks**
  (each chunk ≈ 1 token); tokens are taken from the usage field when
  present, else 0.
- **TPS is per-request**: output tokens / (Total − TTFB).
- **Non-streamed runs omit TTFB/TTFT/TPOT** from text and JSON reports
  rather than reporting them equal to Total.

### Tests

Per-format tests use `httptest` fake servers that verify the request body
(fields, stream flag, auth headers) and return canned SSE/JSON responses —
covering every case, HTTP error paths, non-conforming responses, and
basic-gating. The `cmd` integration test drives all 17 cases end-to-end
against a 3-format mock in streamed and `--no-stream` modes, and round-trips
the `-o` JSON reports against the schema above.

## cache — cache hit-rate test (session-shaped)

Measures whether prompt caching actually works end-to-end and how effective
it is, shaped like a real agent session (Claude Code / Codex) rather than
repeated identical requests: a stable prefix (system prompt + tool
definitions) plus a conversation history that grows one turn at a time, the
only variation being the newest user question.

The compatibility cases (`messages:cache_control`,
`responses:prompt_cache_key`) only verify that the endpoint *accepts* cache
parameters; they cannot detect a proxy that strips or ignores them. This
command verifies caching end-to-end by observing the cache fields in the
usage of every turn.

Flags:

```
      --api-format string   API format to test: all, chat, messages (default "all")
      --turns int           session turns (default 8)
```

- v1 formats: `chat` (automatic prefix cache, Codex-style) and `messages`
  (explicit `cache_control` breakpoints, Claude Code-style). `responses` is
  excluded — its cache surface is the DeepSeek-specific `prompt_cache_key`,
  lowest value.
- Always non-streamed: cache fields only appear in the final non-streamed
  usage; caching semantics are independent of streaming. `--no-stream` does
  not apply.
- No artificial delay between turns: natural request cadence keeps the
  session inside the cache TTL window. TTL/eviction probing is future work.

### Interface (internal/registry)

```go
// CacheTurn is the observation from one session turn.
type CacheTurn struct {
	Turn          int
	PromptTokens  int           // total prompt tokens this request
	Cached        int           // tokens served from cache (read)
	CacheWrite    int           // tokens written to cache; 0 for chat (automatic cache)
	Total         time.Duration
	Err           error         // non-nil: turn failed, session aborts
}

// CacheCase is one simulated agent session. Turns are strictly sequential:
// each turn grows the conversation history, mirroring real agent usage.
// The session stops at the first failed turn. progress, when non-nil, is
// called with the number of completed turns after each turn.
type CacheCase interface {
	ID() string
	Desc() string
	RunSession(ctx context.Context, model string, turns int, progress func(done int)) []CacheTurn
}
```

Miss tokens per turn are derived: `PromptTokens - Cached - CacheWrite`.

### Metrics

| Metric | Definition |
|---|---|
| session hit rate (token-weighted) | ΣCached / ΣPromptTokens over all turns (matches Claude Code /status semantics) |
| warm hit rate (token-weighted) | turns 2..N only |
| request-level hit rate | warm turns with Cached > 0 / warm turns executed |
| cold vs warm Total | turn 1 vs p50 of turns 2..N; fallback signal when a provider reports no cache fields |

### Error semantics

Any turn failure (HTTP error, timeout) records `Err` on that turn and the
session **aborts immediately** — a broken history makes remaining turns
meaningless. The report shows `failed at turn k`.

### messages — explicit cache_control

Usage adds `cache_creation_input_tokens` and `cache_read_input_tokens`.
Three `cache_control: ephemeral` breakpoints (Anthropic limit is 4),
mirroring Claude Code's layout:

| breakpoint | covers |
|---|---|
| system block | [system] |
| last tool definition | [system + tools] |
| last history message | [system + tools + all history] |

Each turn resends the full previous history plus one new user question; the
breakpoint on the last history message makes the read = everything before the
previous turn's tail, and the write = the two newest messages. Steady-state
read share is 85–95%, matching real sessions.

Session content (shared with chat, in `internal/cases`): a ~2k-token stable
system prompt (persona that instructs the model not to call tools and answer
directly), 6–8 tool definitions with realistic JSON schemas (~2–3k tokens —
the bulk of the prefix, like Claude Code's tool surface), 8 deterministic
short user questions, `max_tokens` ≈ 300.

### chat — automatic prefix cache

Usage adds `prompt_tokens_details.cached_tokens`, plus DeepSeek-style
`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` fallback (DeepSeek
reports those instead). Cached = `cached_tokens`, falling back to
`prompt_cache_hit_tokens` when `prompt_tokens_details` is absent;
`CacheWrite` is always 0. No breakpoints — hits require an exact
token-prefix match above the provider's automatic-cache threshold (≈1k
tokens; our prefix is several k). Turn 1 is a full miss; hits are observable
from turn 2.

### Verdicts

| Verdict | Condition |
|---|---|
| cache observed | any warm turn with Cached > 0 |
| no cache observed | session completed, Cached == 0 on every turn (a valid outcome: the endpoint's caching does not work) |
| inconclusive | session aborted with no hits before the failure |

### Tests

Per-format httptest servers verify the request shape (breakpoint placement,
growing history, tools present) and return canned usage; an error mid-session
aborts at the failing turn. Runner tests cover the aggregation math and all
three verdicts. The cmd integration test drives `cache` end-to-end against
chat+messages mocks and round-trips the `-o` JSON.
